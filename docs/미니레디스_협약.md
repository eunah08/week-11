# 미니 레디스 협약

> 이 문서는 팀원 모두와 AI가 같은 기준으로 코드를 짜기 위한 약속이다. 여기에 적힌 이름과 형태가 코드보다 우선한다. 바꾸고 싶으면 코드를 먼저 고치지 말고 이 문서를 먼저 고친다.
> 허준강, 조은아, 문상균 세 사람의 협약 초안을 취합해 만든 통합본이다. Phase 1(엔진)과 Phase 2(서버) 내용을 한 문서에 담는다.

## 0. 문서 사용법

- 대상 독자 : 팀원, AI
- 우선순위 : 이 문서 > 개별 코드
- 이 문서의 위치 : `Redis-develop` 브랜치의 `docs/미니레디스_협약.md`
- 변경 방법 : 팀원 전원 합의 후 문서를 먼저 수정하고, 20장 변경 이력에 기록한다
- 상태 : 세 초안 취합본 (팀 검토 필요)
- AI에게 일을 시킬 때는 이 문서의 장 번호를 가리킨다 (예: "8.2의 store_get만 구현해")

### 적용 수준

학습보다 구현이 우선이다. 가독성과 수정 용이성을 우선하며, 모듈의 경계와 공개 함수·외부 API의 모양은 통일한다. 해시 함수, 충돌 처리, 내부 자료구조, 동시성 구조, 보조 함수는 각자 선택한다. 단, 핵심 로직(해시 테이블, 만료, 동시성)은 만든 사람이 AI 없이 직접 설명할 수 있어야 한다.

- 필수 : 모든 구현이 따라야 한다.
- 권장 : 기본적으로 따르되, 다른 선택의 이유를 설명할 수 있다.
- 자율 : 공통 인터페이스를 지키는 범위에서 각자 선택한다.

별도 표시가 없는 규칙은 필수다.

## 1. 프로젝트 개요와 일정

- 프로젝트 이름 : 미니 레디스 구현
- 한 줄 목표 : 직접 만든 해시 테이블로 키-값 저장소를 만들고, 외부에서 HTTP API로 쓸 수 있게 한다
- 최종 결과물 :
    - 미니 레디스 서버 (HTTP + JSON API)
    - 미니 레디스를 캐시로 쓰는 샘플 API
    - 캐시 사용 전후의 성능 비교 결과

### 1.1. 작업 방식

- 세 사람이 각자 완성본을 구현한다.
- 각 Phase가 끝나면 코어타임에 세 구현을 검토하고, 하나를 고르거나 장점을 합쳐 `Redis-develop`에 병합한다.
- 세 서버는 같은 요청에 같은 결과를 돌려줘야 한다. 그래서 8장의 공통 헤더와 11장의 외부 API는 글자 하나까지 맞춘다.
- 팀원은 요청 처리부터 직접 구현한 해시 테이블까지의 경로를 코드로 설명할 수 있어야 한다.

### 1.2. 구현 단계

| 단계 | 내용 |
|---|---|
| Phase 1 (엔진) | 해시 테이블, `store` 저장·조회·삭제, TTL 만료, 무효화, 단위 테스트 |
| Phase 2 (서버) | HTTP API 서버, 동시성 구조, 주기적 만료 정리, 캐시 샘플 API, 기능 테스트, 성능 비교 |
| Phase 2 (선택) | 영속성 (AOF) |
| 차별화 | 19장 미정 사항의 후보 중 선택 |

- 단계 구분 이유 : TTL과 무효화는 저장소 안에서 결정되므로 네트워크 없이 단위 테스트로 검증할 수 있다. 동시성은 여러 요청이 동시에 들어오는 서버에서 생기는 문제라서 API와 함께 정한다.

### 1.3. 과제 요구사항과 이 문서의 연결

## 2. 기술 기준

| 항목 | 규칙 |
|---|---|
| 구현 언어 | C (C11) |
| 실행 환경 | POSIX (Linux, macOS). Windows는 WSL에서 실행한다 |
| 빌드 | `Makefile`. `make`, `make test`, `make run`이 동작해야 한다 |
| 컴파일 옵션 | `-std=c11 -Wall -Wextra`. 경고 없이 빌드되어야 한다 |
| 통신 | HTTP/1.1 + JSON |
| 기본 포트 | 미니 레디스 `6380`, 샘플 API `3000`. 상수로 두고 실행 인자로 바꿀 수 있게 한다 |
| 개발·테스트 도구 | 지정하지 않는다. 각자 자유롭게 선택한다 |

### 2.1. 직접 구현해야 하는 것 (필수)

- 해시 테이블은 배열과 직접 만든 노드로 구현한다. `hsearch`(`search.h`), glib `GHashTable`, `uthash` 같은 기존 해시 테이블을 저장소 본체로 쓰지 않는다.
- TTL 만료 처리, 무효화, 동시성 제어의 핵심 로직을 외부 라이브러리로 대체하지 않는다.
- 미니 레디스 대신 실제 Redis를 쓰지 않는다. 성능 비교의 기준도 "캐시 없음"이지 "실제 Redis"가 아니다.

### 2.2. 써도 되는 것 (자율)

- HTTP 요청 파싱, JSON 파싱(예: cJSON), HTTP 클라이언트(예: libcurl) 라이브러리는 써도 된다. 단, 11.4의 검증 규칙(중복 필드 판정 등)을 지킬 수 있어야 한다.
- 테스트 도구, 성능 측정 도구(`wrk`, `hey`, 스크립트 등)는 자유다.
- 사용한 외부 라이브러리는 `README.md`와 `implementation_notes.md`에 적는다.

## 3. 브랜치와 협업 규칙

### 3.1. 브랜치 구성

| 브랜치 | 역할 | 누가 바꾸나 |
|---|---|---|
| `Redis` | 미니 레디스의 main. 최종 통합본 | 최종 통합 코어타임 후 병합 |
| `Redis-develop` | 미니 레디스의 develop. 단계마다 고른 구현이 쌓인다 | 각 Phase 코어타임 후 병합 |
| `feat/redis_<단계>_<이니셜>` | 개인 작업 브랜치 | 본인 |

- 개인 브랜치 예 : `feat/redis_1_sk`, `feat/redis_2_jk`, 차별점은 `feat/redis_extra_<이니셜>`
- 이니셜은 각자 정하고, 모든 단계에서 같은 이니셜을 쓴다.
- 대소문자만 다른 브랜치(`develop`과 `Develop` 등)를 만들지 않는다. Windows가 구분하지 못한다.

### 3.2. 단계별 작업 흐름

1. 최신 `Redis-develop`에서 `feat/redis_1_<이니셜>`을 만들어 Phase 1을 작업하고 원격에 올린다.
2. 코어타임에 세 구현을 검토하고, 하나를 고르거나 장점을 합쳐 `Redis-develop`에 병합한다.
3. 병합된 `Redis-develop`을 pull 받은 뒤 `feat/redis_2_<이니셜>`을 만들어 Phase 2를 작업한다.
4. Phase 2도 코어타임 검토 후 `Redis-develop`에 병합한다.
5. 최종 통합 코어타임 후 `Redis-develop`을 `Redis`에 병합한다.

- `Redis`와 `Redis-develop`에는 코어타임 검토 없이 병합하지 않는다.
- 다음 단계는 반드시 병합된 구현 위에서 시작한다. 각자 자기 Phase 1 위에 Phase 2를 쌓지 않는다.
- 병합은 PR로 하고, PR 설명에 "고른 구현과 이유"를 한 줄 남긴다.
- 협약 문서 수정은 팀 합의 후 `Redis-develop`에 커밋하고, 각자 개인 브랜치로 pull 받는다.

### 3.3. 커밋 메시지 (권장)

- 형식 : `종류: 한글 설명` (예: `feat: 해시 테이블 rehash 구현`)
- 종류 : `feat`(기능), `fix`(버그), `refactor`(동작 변화 없는 정리), `test`(테스트), `docs`(문서), `style`(형식)
- 한 커밋에는 한 가지 일만 담는다.

## 4. 코딩 컨벤션

### 4.1. C 이름 규칙

| 대상 | 규칙 | 예시 |
|---|---|---|
| 파일·폴더 | 소문자 `snake_case` | `hash_table.c`, `api_errors.h` |
| 함수 | `모듈이름_동사_대상` 형태의 `snake_case` | `store_set`, `hash_table_find_entry` |
| 변수·매개변수 | `snake_case` | `bucket_index`, `expires_at_ms` |
| 구조체·열거형 타입 | `snake_case` + `_t` | `store_t`, `store_status_t` |
| 상수·매크로·열거 값 | `UPPER_SNAKE_CASE` | `MAX_LOAD_FACTOR`, `STORE_NOT_FOUND` |
| 참·거짓 값과 함수 | `is_`, `has_`, `can_`으로 시작 | `is_expired`, `has_key` |
| 내부 함수 | 파일 안에서만 쓰면 `static` | `static size_t find_bucket_index(...)` |
| 테스트 파일 | `test_대상.c` | `test_hash_table.c` |

- 헤더 파일에는 include guard(`#ifndef STORE_H` …)를 넣는다.
- 외부 API의 JSON 필드 이름은 `camelCase`(`ttlMs`, `deletedCount`)로 쓴다. C 코드 안에서는 같은 개념을 `snake_case`(`ttl_ms`, `deleted_count`)로 쓴다.

### 4.2. 코드 형식

- 들여쓰기 : 공백 4칸
- 줄 길이 : 100자
- 중괄호 : 함수와 제어문 모두 같은 줄에 연다
- 조건문·반복문 : 한 줄이어도 중괄호를 쓴다
- 포인터 표시 : `char *key` (별표를 변수 쪽에 붙인다)
- 파일 마지막 : 줄바꿈 1개
- 포매터 : `clang-format` 사용 (권장). 설정 파일은 19장 미정 사항에서 정한다

### 4.3. 용어와 변수 이름

같은 개념을 여러 이름으로 섞어 쓰지 않는다.

| 개념 | C 코드 | JSON 필드 |
|---|---|---|
| 저장소 전체 | `store` | |
| 해시 테이블 | `hash_table` | |
| 칸 목록 / 칸 하나 | `buckets` / `bucket` | |
| 저장된 항목 하나 (키·값·만료 시각) | `entry` | |
| 키, 값 | `key`, `value` | `key`, `value` |
| 저장된 항목 수 | `size` | `size` |
| 칸 개수 | `capacity` | `capacity` |
| 적재율 | `load_factor` | |
| 만료 시각 (단조 시계 기준, 밀리초) | `expires_at_ms` | |
| 남은 보관 시간 (밀리초) | `ttl_ms` | `ttlMs` |
| 현재 시각을 읽는 함수 | `now_ms` | |

- 줄임말은 누구나 아는 것만 쓴다. 허용 목록 : `id`, `ttl`, `api`, `url`, `http`, `json`, `max`, `min`, `ms`, `len`, `buf`, `aof`, `fd`. 그 밖의 줄임말(`cnt`, `tmp`, `res` 등)은 쓰지 않는다.
- 한 글자 이름은 짧은 반복문의 `i`, `j`만 허용한다. 한글 이름은 쓰지 않는다.
- 시간·크기처럼 단위가 있으면 이름에 넣는다. 예 : `ttl_ms`, `size_bytes`
- 여러 개면 복수형, 개수면 `_count`를 붙인다.
- 숫자·문자열을 바로 쓰지 않고 상수로 이름을 붙인다. 예 : `0.75` 대신 `MAX_LOAD_FACTOR`

### 4.4. 함수 이름과 설계

- 이름은 "동사 + 대상"으로 짓는다. 같은 뜻에는 같은 동사를 쓴다.

| 동사 | 뜻 |
|---|---|
| `get` | 반드시 있는 값을 가져온다 (내부 함수) |
| `find` | 없을 수도 있다 (없으면 `NULL`) |
| `create` / `destroy` | 만들고 메모리를 확보한다 / 메모리까지 모두 해제한다 |
| `remove` | 항목을 없앤다 (내부 함수) |
| `update` | 이미 있는 것을 고친다 |
| `parse` / `to_` | 다른 형식으로 바꾼다 |
| `is` / `has` | 참·거짓을 돌려준다 |

- 예외 : 8장의 공개 함수(`store_get`, `store_delete`, `store_exists` 등)는 실제 Redis 명령 이름을 따른다. 그래서 `store_get`은 없으면 "없음"(`STORE_NOT_FOUND`)을 돌려주고, 지우는 공개 함수는 `remove` 대신 `delete`를 쓴다.
- 함수 하나는 한 가지 일만 한다. 이름에 "그리고"가 들어가야 설명되면 나눈다.
- 한 함수는 30줄을 넘기지 않고, 중첩은 3단계까지 쓴다. 넘으면 함수를 쪼갠다.
- 인자는 3개 이하로 한다. 첫 번째 인자인 대상 객체(`store_t *store` 등)와 결과를 받는 출력 포인터(`out_…`)는 개수에서 뺀다. 넘으면 옵션 구조체 하나로 묶는다.
- 받은 값을 함부로 고치지 않는다. 입력 포인터는 가능하면 `const`로 받는다. 전역 변수에 결과를 저장하지 않는다.

### 4.5. 메모리 규칙

- `malloc`/`calloc`/`realloc`의 반환값은 항상 확인한다. 실패하면 `STORE_ERR_NO_MEMORY`(또는 `500 INTERNAL_ERROR`)로 처리하고, 프로세스를 죽이지 않는다.
- 메모리를 확보한 쪽과 해제할 쪽을 공개 함수의 문서 주석에 적는다. (8.1 참고)
- 해제한 포인터는 `NULL`로 바꾼다.
- 단위 테스트는 AddressSanitizer(`-fsanitize=address`) 또는 Valgrind로 메모리 오류와 누수 없이 통과해야 한다. (권장)

### 4.6. 주석

- 공개 함수 위에는 문서 주석을 단다. 입력, 반환값, 실패할 때의 동작, 상태 변경 여부, 메모리 해제 책임, 시간 복잡도를 적는다.
- 함수 안 주석은 "어떻게"가 아니라 "무엇을, 왜"를 쓴다. 코드만 봐서는 알 수 없는 이유, 조건, 주의할 점만 적는다.
- 주석은 한국어로 쓴다. 할 일은 `TODO(이니셜): 내용` 형식으로 남긴다.
- 지운 코드를 주석으로 남겨 두지 않는다.

### 4.7. 시간

- 만료 계산에는 시스템 시각이 바뀌어도 거꾸로 가지 않는 단조 시계(`clock_gettime(CLOCK_MONOTONIC)`)를 쓴다.
- 현재 시각을 읽는 곳은 한 함수(`now_ms`)로 모은다. `store`는 이 함수를 주입받아서만 시각을 읽는다. 테스트에서 시각을 바꿔 끼워 TTL을 기다리지 않고 검증하기 위해서다.
- 실제 시각(`CLOCK_REALTIME`)은 영속성 파일에 만료 시각을 적을 때만 쓴다. (14장)

- 위 트리에 없는 최상위 폴더를 새로 만들지 않는다. 필요하면 먼저 이 문서를 고친다.

- `tests/api/`의 외부 기능 테스트는 언어가 자유다 (셸 + `curl`, Python 등). 서버 주소만 바꾸면 세 서버에 똑같이 돌 수 있어야 한다.

## 6. 모듈 책임과 의존 관계

| 모듈 | 책임 |
|---|---|
| `hash_table` | 해싱, 충돌 처리, 항목의 삽입·탐색·삭제, rehash. 시간·만료·네트워크를 모른다 |
| `store` | 키·값 연산, TTL 만료 판단, 무효화, 통계. 네트워크·파일을 모른다 |
| `server` | 요청 해석·검증, `store` 결과를 응답으로 변환, 동시성 제어, 주기적 만료 정리 호출 |
| `demo` | 느린 원본 API와 그 응답을 미니 레디스에 캐시하는 예제 |
| `bench` | 캐시 있음·없음 성능 측정 |
| `persistence` (선택) | 쓰기 기록과 시작 시 복구 |

### 필수 경계

- 의존 방향은 `demo·bench → (HTTP API) → server → store → hash_table`이다. 반대 방향 의존은 금지한다.
- `hash_table`은 `store`, `server`를 include하지 않는다.
- `store`는 `server`, `persistence`를 include하지 않는다. 순수한 메모리 저장소다.
- `server`는 해시 테이블 내부(`buckets` 등)를 직접 만지지 않고 8장의 공개 함수만 쓴다.
- `demo`와 `bench`는 미니 레디스를 HTTP API로만 쓴다. `store`를 직접 링크하지 않는다. (외부 사용자와 같은 입장에서 검증하기 위해)
- `persistence`는 `store`의 공개 함수로만 데이터를 넣고 뺀다.

## 7. 저장소 데이터 형식 (Phase 1)

### 7.1. 키와 값

- 키 : 비어 있지 않은 UTF-8 문자열. 길이는 1~256바이트 (`MAX_KEY_BYTES = 256`)
- 값 : 문자열만 저장한다. 빈 문자열도 저장할 수 있고 "없음"과 구분된다. 최대 1MiB (`MAX_VALUE_BYTES = 1048576`)
- 숫자·객체는 저장하는 쪽이 문자열(JSON 등)로 바꿔서 넣는다. 리스트·해시 같은 다른 자료형은 차별화 후보로 둔다.
- 키와 값은 입력 그대로 보존한다. (앞뒤 공백 제거, 대소문자 변환 금지)
- C 문자열의 끝 표시와 겹치므로 NUL 문자(`\u0000`)가 들어간 키·값은 받지 않는다.

### 7.2. 항목 (`entry`)

| 필드 | 뜻 |
|---|---|
| `key` | 키 (store가 복사해서 보관) |
| `value` | 값 (store가 복사해서 보관) |
| `expires_at_ms` | 만료 시각 (단조 시계 기준). 만료가 없으면 `NO_EXPIRY`(0) |

- 필드 이름과 추가 필드(`next` 포인터 등)는 구현에 맞게 둔다. 뜻은 같아야 한다.

## 8. 공개 함수 규칙 (Phase 1)

### 8.1. 공통 헤더 `store.h` (필수)

세 구현이 모두 같은 헤더를 쓴다. 그래서 단위 테스트를 서로의 구현에 그대로 돌릴 수 있다.

```c
#ifndef STORE_H
#define STORE_H

#include <stdbool.h>
#include <stddef.h>
#include <stdint.h>

#define STORE_NO_TTL 0                  /* store_set에서 "만료 없음" */
#define STORE_TTL_NO_EXPIRY (-1)        /* store_ttl 결과: 만료 없음 */
#define MAX_KEY_BYTES 256
#define MAX_VALUE_BYTES 1048576
#define MAX_TTL_MS 2147483647

typedef enum {
    STORE_OK = 0,
    STORE_NOT_FOUND,             /* 없거나 만료됨. 에러가 아니다 */
    STORE_ERR_INVALID_KEY,       /* NULL, 빈 키, 256바이트 초과 */
    STORE_ERR_INVALID_VALUE,     /* NULL 값 */
    STORE_ERR_VALUE_TOO_LARGE,   /* 1MiB 초과 */
    STORE_ERR_INVALID_TTL,       /* 1~MAX_TTL_MS 밖 */
    STORE_ERR_INVALID_PREFIX,    /* NULL 또는 빈 접두사 */
    STORE_ERR_NO_MEMORY
} store_status_t;

typedef uint64_t (*store_clock_fn)(void);   /* 단조 시계, 밀리초 */

typedef struct {
    size_t initial_capacity;     /* 0이면 구현 기본값 */
    store_clock_fn now_ms;       /* NULL이면 clock.c의 기본 단조 시계 */
} store_options_t;

typedef struct {
    size_t size;
    size_t capacity;
    uint64_t hit_count;
    uint64_t miss_count;
    uint64_t expired_count;
} store_stats_t;

typedef struct store store_t;   /* 내부 구조는 각자 store.c에서 정의 */

store_t *store_create(const store_options_t *options);
void store_destroy(store_t *store);

store_status_t store_set(store_t *store, const char *key, const char *value,
                         int64_t ttl_ms, bool *out_is_created);
store_status_t store_get(store_t *store, const char *key, char **out_value);
store_status_t store_delete(store_t *store, const char *key, bool *out_is_deleted);
store_status_t store_exists(store_t *store, const char *key, bool *out_exists);
store_status_t store_expire(store_t *store, const char *key, int64_t ttl_ms,
                            bool *out_is_applied);
store_status_t store_ttl(store_t *store, const char *key, int64_t *out_ttl_ms);
size_t store_size(store_t *store);
store_status_t store_delete_by_prefix(store_t *store, const char *prefix,
                                      size_t *out_deleted_count);
size_t store_remove_expired(store_t *store, size_t max_count);
void store_get_stats(store_t *store, store_stats_t *out_stats);

#endif
```

- `store_create`는 메모리가 부족하면 `NULL`을 돌려준다.
- `store_set`은 키와 값을 복사해서 보관한다. 호출한 쪽은 넘긴 문자열을 바로 해제해도 된다.
- `store_get`은 값의 복사본을 `*out_value`에 넣는다. 호출한 쪽이 `free()`로 해제한다. 실패하면 `*out_value`는 `NULL`이다.
- 출력 포인터(`out_…`)에 `NULL`을 넘기면 그 결과는 받지 않는다는 뜻이다. (`store_get`의 `out_value` 제외)
- 입력 검증은 공개 함수의 맨 앞에서만 하고, 검증에 실패하면 상태를 전혀 바꾸지 않는다. 내부 함수는 검증된 입력을 믿는다.

### 8.2. 함수별 경계

| 함수 | 하는 일 | 결과 |
|---|---|---|
| `store_set` | 값과 만료 기한을 함께 저장한다. 이미 있으면 덮어쓴다 | `out_is_created` : 새로 만들었으면 참, 덮어썼으면 거짓 |
| `store_get` | 값을 가져온다 | `STORE_OK` + 값 복사본, 없거나 만료면 `STORE_NOT_FOUND` |
| `store_delete` | 항목을 지운다 | `out_is_deleted` : 지웠으면 참, 없었거나 만료였으면 거짓 |
| `store_exists` | 살아 있는 항목이 있는지 | `out_exists` |
| `store_expire` | 이미 있는 항목에 만료 시간을 다시 건다 | `out_is_applied` : 걸었으면 참, 없거나 만료였으면 거짓 |
| `store_ttl` | 남은 보관 시간 | 남은 밀리초, 만료 없음은 `-1`, 없거나 만료면 `STORE_NOT_FOUND` |
| `store_size` | 살아 있는 항목 수 | 정수 |
| `store_delete_by_prefix` | 접두사가 같은 키를 모두 지운다 | 지운 개수 (만료 키는 세지 않는다) |
| `store_remove_expired` | 만료된 항목을 최대 `max_count`개 정리한다 | 정리한 개수 |
| `store_get_stats` | 통계 | `store_stats_t` |

- 함수 이름은 실제 Redis 명령(`SET`, `GET`, `DEL`, `EXISTS`, `PEXPIRE`, `PTTL`, `DBSIZE`)과 짝을 맞췄다.
- `store_get`이 성공하면 `hit_count`, `STORE_NOT_FOUND`이면 `miss_count`를 1 올린다.

### 8.3. `store_set`

- 같은 키로 다시 저장하면 값과 만료 기한을 모두 새로 덮어쓴다. `ttl_ms`가 `STORE_NO_TTL`(0)이면 기존 만료가 없어진다. (실제 Redis `SET`과 같은 동작)
- `ttl_ms`가 음수이거나 `MAX_TTL_MS`보다 크면 `STORE_ERR_INVALID_TTL`이다.
- 만료된 키에 저장하면 새로 만든 것으로 본다. (`out_is_created`가 참)
- 저장 후 적재율이 기준을 넘으면 칸을 늘린다(rehash). 기준값과 늘리는 배수는 자율이다.

### 8.4. 무효화

원문 : "사용자가 Redis에 저장된 데이터를 무효화(deprecated)하는 방식에 대해 고민해 봅니다."

| 방식 | 함수 | API | 적용 수준 |
|---|---|---|---|
| 키 하나를 바로 지운다 | `store_delete` | `DELETE /keys/{key}` | 필수 |
| 일정 시간 뒤 자동으로 무효가 되게 한다 (TTL 단축) | `store_set`, `store_expire` | `PUT /keys/{key}/ttl` | 필수 |
| 접두사가 같은 키를 한꺼번에 지운다 | `store_delete_by_prefix` | `POST /invalidate` | 필수 |
| 전체를 비운다 | `store_flush` | `POST /flush` | 선택 |

- 키 이름은 실제 Redis 관례처럼 콜론으로 구분한다. 예 : `product:42`, `user:42:profile`
- 빈 접두사는 `STORE_ERR_INVALID_PREFIX`다. 전체 삭제는 `flush`로만 한다.
- `store_delete_by_prefix`는 테이블 전체를 훑으므로 O(n)이다. 알려진 제한으로 문서화한다.
- 무효화 후 다시 조회하면 없음이고, 호출한 쪽이 원본에서 다시 가져와 저장하는 것이 기본 사용 방식이다. (13장 Cache-Aside)

### 8.5. 선택 함수

선택 기능을 구현하면 아래 이름과 모양을 쓴다. `store.h`에 추가하되, 구현하지 않은 사람의 헤더와 충돌하지 않게 선택 함수는 헤더 끝에 모은다.

| 함수 | 하는 일 |
|---|---|
| `store_status_t store_increase(store_t *store, const char *key, int64_t amount, int64_t *out_value)` | 값을 정수로 읽어 더하고 문자열로 다시 저장한다. 없는 키는 0에서 시작. 정수가 아니면 `STORE_ERR_NOT_A_NUMBER` (enum에 추가) |
| `void store_flush(store_t *store)` | 전체를 비운다 |
| `store_status_t store_find_keys(store_t *store, const char *prefix, char ***out_keys, size_t *out_count)` | 살아 있는 키 목록. 호출한 쪽이 해제한다 |

### 8.6. 구현 자율 범위

- 해시 함수(FNV-1a, djb2 등), 충돌 처리 방식(체이닝·개방 주소법), 처음 칸 개수, rehash 기준과 방식(한 번에·점진적)은 자율이다.
- 단, 어떤 방식을 골랐는지와 그 이유, 평균·최악 시간 복잡도를 `implementation_notes.md`에 쓴다.
- 칸 개수를 줄이는 기능은 필수가 아니다. 지원하지 않으면 알려진 제한으로 적는다.

## 9. TTL 만료 처리 규칙

원문 : "보관 기간이 만료된 값을 요청받았을 때, 이를 어떻게 처리할지 방안을 마련합니다."

- TTL은 `store_set`·`store_expire`가 적용된 시점부터 지난 시간으로 계산한다. `expires_at_ms = now_ms() + ttl_ms`
- 지난 시간이 TTL 이상이면 만료다. 만료 시각 정각(`expires_at_ms <= now_ms()`)도 만료로 본다.
- 시스템 날짜·시각을 바꿔도 만료 판정이 달라지지 않아야 한다. (단조 시계)
- 만료된 항목은 모든 공개 함수에서 "없는 항목"과 똑같이 보인다. `get`, `delete`, `exists`, `expire`, `ttl`, `size`, `delete_by_prefix` 모두 해당한다.

### 9.1. 지연 삭제 (필수)

- 키를 읽는 공개 함수가 만료된 항목을 만나면 그 자리에서 지우고 없는 키처럼 처리한다.
- 지울 때 `expired_count`를 1 올린다.

### 9.2. 주기적 정리 (필수)

- 아무도 다시 찾지 않는 만료 키가 메모리에 쌓이지 않게, 서버가 `SWEEP_INTERVAL_MS`(기본 1000)마다 `store_remove_expired(SWEEP_BATCH_SIZE)`(기본 200)를 부른다.
- 한 번에 처리하는 양에 상한을 둬서 다른 요청을 오래 막지 않는다.
- 정리 대상 선택 방식(전체 순회, 일부 칸만 돌아가며 확인 등)은 자율이며 `implementation_notes.md`에 적는다.
- 정리 작업은 12장의 동시성 규칙 안에서 실행한다. 만료 판정과 삭제 사이에 다른 요청이 같은 키를 다시 저장할 수 있다면, 삭제 직전에 동기화 경계 안에서 현재 항목의 만료 여부를 다시 확인한다.
- `sweeper_start()`, `sweeper_stop()`을 둔다. 서버 종료 시 반드시 멈추고(스레드라면 join) 자원을 남기지 않는다.
- `store_size()`가 만료 항목을 세지 않도록 한다. 정확히 세기 어려운 방식을 골랐다면 그 한계를 문서화한다.

### 9.3. 클라이언트가 보는 결과

- 만료된 키 조회 : `404 KEY_NOT_FOUND`. 만료와 원래 없음을 구분하지 않는다.

## 10. Phase 1 데이터 흐름

```text
store_set(key, value, ttl_ms)
  → 입력 검증 → 해시로 칸 찾기 → 같은 키가 있으면 값·만료 덮어쓰기, 없으면 추가
  → 만료 시각 = now_ms() + ttl_ms (ttl_ms가 0이면 만료 없음) → 적재율 확인 → 필요하면 rehash

store_get(key)
  → 입력 검증 → 해시로 칸 찾기 → 항목 찾기
  → 없으면 STORE_NOT_FOUND / 만료됐으면 지우고 STORE_NOT_FOUND / 아니면 값 복사본
```

## 11. HTTP API 규칙 (Phase 2)

원문 : "외부에서도 Mini Redis를 쉽게 사용할 수 있도록 API 형태의 구조를 설계해 봅니다."

### 11.1. 필수 엔드포인트

| 메서드와 경로 | 대응하는 함수 | 요청 본문 | 성공 응답 |
|---|---|---|---|
| `PUT /keys/{key}` | `store_set` | `{"value": "…", "ttlMs": 5000}` (`ttlMs` 생략 가능) | `200 {"created": true}` 또는 `{"created": false}` |
| `GET /keys/{key}` | `store_get` | 없음 | `200 {"value": "…"}` |
| `DELETE /keys/{key}` | `store_delete` | 없음 | `200 {"deleted": true}` 또는 `{"deleted": false}` |
| `PUT /keys/{key}/ttl` | `store_expire` | `{"ttlMs": 5000}` | `200 {"applied": true}` 또는 `{"applied": false}` |
| `GET /keys/{key}/ttl` | `store_ttl` | 없음 | `200 {"ttlMs": 4980}` (만료 없으면 `-1`) |
| `POST /invalidate` | `store_delete_by_prefix` | `{"prefix": "product:"}` | `200 {"deletedCount": 3}` |
| `GET /stats` | `store_get_stats` | 없음 | `200 {"size", "capacity", "hitCount", "missCount", "expiredCount"}` |

- 경로의 키는 URL 인코딩해서 보낸다. 서버는 퍼센트 인코딩을 풀어서 쓴다. 잘못된 인코딩이나 빈 키(`/keys/`)는 `400 INVALID_KEY`다.
- `GET`에서 없거나 만료된 키, `GET /keys/{key}/ttl`에서 없거나 만료된 키는 `404 KEY_NOT_FOUND`다.
- `DELETE`와 `PUT /ttl`은 키가 없어도 에러가 아니다. 여러 번 호출해도 결과가 같게 `false`를 돌려준다.
- 같은 키에 `ttlMs` 없이 `PUT`하면 기존 만료가 없어진다. (8.3)

### 11.2. 선택 엔드포인트

| 메서드와 경로 | 대응하는 함수 | 요청 본문 | 성공 응답 |
|---|---|---|---|
| `GET /keys/{key}/exists` | `store_exists` | 없음 | `200 {"exists": true}` |
| `POST /keys/{key}/increase` | `store_increase` | `{"amount": 1}` (생략하면 1) | `200 {"value": "11"}` |
| `GET /keys?prefix=…` | `store_find_keys` | 없음 | `200 {"keys": [ … ]}` (최대 `MAX_KEYS_PER_RESPONSE` = 1000개) |
| `POST /flush` | `store_flush` | 없음 | `200 {"flushed": true}` |
| `GET /health` | 없음 | 없음 | `200 {"status": "ok"}` |

### 11.3. 응답 형식

- 모든 응답 본문은 JSON이고 `Content-Type: application/json; charset=utf-8`이다.
- 성공 응답은 11.1의 단순한 모양을 쓴다.
- 에러 응답은 `{"error": {"code": "INVALID_TTL", "message": "[store_set] ttlMs는 1~2147483647 사이의 정수여야 합니다"}}` 모양이다.
- `message` 형식은 `[함수이름] 한글 설명`이다. 내부 경로, 스택, 메모리 주소를 담지 않는다.

| 상황 | 상태 코드 | `code` |
|---|---|---|
| 본문이 JSON이 아님 | `400` | `INVALID_JSON` |
| 최상위가 객체가 아님, 필수 필드 누락, 정의되지 않은 필드, 중복 필드, 필드 타입 오류 | `400` | `INVALID_BODY` |
| 키 형식 오류 (빈 키, 256바이트 초과, NUL 포함, 잘못된 URL 인코딩) | `400` | `INVALID_KEY` |
| `value`가 문자열이 아님, NUL 포함 | `400` | `INVALID_VALUE` |
| `ttlMs`가 범위 밖이거나 정수가 아님 | `400` | `INVALID_TTL` |
| `prefix`가 빈 문자열이거나 형식 오류 | `400` | `INVALID_PREFIX` |
| 키가 없거나 만료됨 | `404` | `KEY_NOT_FOUND` |
| 정의되지 않은 경로 | `404` | `ROUTE_NOT_FOUND` |
| 허용하지 않는 메서드 | `405` | `METHOD_NOT_ALLOWED` |
| 숫자가 아닌 값에 `increase` (선택) | `409` | `NOT_A_NUMBER` |
| 값이 `MAX_VALUE_BYTES` 초과 | `413` | `VALUE_TOO_LARGE` |
| 본문이 `MAX_BODY_BYTES` 초과 | `413` | `PAYLOAD_TOO_LARGE` |
| 서버 내부 오류, 메모리 부족 | `500` | `INTERNAL_ERROR` |

- 잘못된 입력은 모두 `400`으로 통일하고, 종류는 `code`로 구분한다.
- `store_status_t`와 에러 코드·상태 코드의 대응은 `api_errors.c`의 표 하나에 모은다.

### 11.4. 입력 검증 규칙

- 요청 본문은 최상위 JSON 객체여야 한다.
- 정의되지 않은 필드가 있으면 거부한다.
- 같은 필드가 두 번 나오면 거부한다. 중복은 JSON 이스케이프를 해석한 뒤의 필드 이름으로 판정한다. (`"ttlMs"`와 `"ttl\u004ds"`는 같은 필드)
- `value`와 `prefix`는 문자열이어야 한다. 빈 문자열 `value`는 허용한다.
- `ttlMs`는 1~2,147,483,647 범위의 정수 값을 가진 JSON 숫자다. `1.0`은 허용하고 `1.5`, `"1"`, `0`, `-1`, `null`은 거부한다.
- 검증은 상태를 바꾸기 전에 모두 끝낸다. 거부된 요청은 기존 값과 만료 기한을 그대로 둔다.

### 11.5. 서버 보호

- 요청 본문은 `MAX_BODY_BYTES`(기본 2MiB)까지만 읽고, 넘으면 읽기를 멈추고 `413`을 돌려준다. 값 한도(1MiB)보다 크게 잡는 이유는 JSON 이스케이프로 본문이 길어질 수 있어서다.
- 본문이 있는 요청은 `Content-Length`가 있어야 한다. `chunked` 전송은 지원하지 않아도 된다 (`400 INVALID_BODY`).
- 어떤 입력이 와도 서버 프로세스가 죽으면 안 된다.
    - 끊긴 연결에 쓸 때 프로세스가 죽지 않게 `SIGPIPE`를 무시하거나 `MSG_NOSIGNAL`을 쓴다.
    - 입력으로 `assert`나 `exit`를 부르지 않는다.
    - 메모리 할당 실패는 `500`으로 돌려주고 `stderr`에 남긴다.
- `SIGINT`·`SIGTERM`을 받으면 새 요청을 멈추고, 정리 작업을 멈추고, 저장소를 해제한 뒤 종료한다.
- `keep-alive` 지원은 자율이다. 성능 비교 때는 세 구현이 같은 연결 방식을 쓴다.

### 11.6. 클라이언트 모듈 (선택)

- `demo`가 쓰는 HTTP 호출을 함수로 감싼 얇은 포장이다. 만든다면 `src/client/`에 둔다.
- 서버가 `404 KEY_NOT_FOUND`를 주면 "없음"으로 돌려주고 에러로 보지 않는다. 연결 실패나 시간 초과는 에러로 돌려준다.

## 12. 동시성 규칙 (Phase 2)

원문 : "동시성 문제가 발생하지 않도록 하려면 어떤 아키텍처 또는 구조를 가져야 할지 고민해 봅니다."

### 12.1. 보장 사항 (필수)

- 같은 키에 대한 각 명령은 한 시점에 적용된 것처럼 보여야 한다. 값이 반쯤 쓰인 상태로 읽히지 않는다.
- `PUT` 성공 응답 뒤에 시작된 `GET`은 덮어쓰기·삭제·만료 전까지 저장된 값을 돌려준다. 다른 키의 동시 저장, 충돌 처리, rehash 중에도 마찬가지다.
- 같은 키를 동시에 삭제하면 `deleted: true`는 한 번만 나온다.
- 같은 키에 동시에 여러 번 저장하면 그중 하나의 값만 온전히 남는다.
- 읽고 → 판단하고 → 쓰는 흐름(`increase`, 지연 삭제, 만료 정리)은 한 번의 동기화 경계 안에서 끝낸다.
- 서버가 멈추거나(교착 상태) 죽지 않는다.

### 12.2. 구조 선택 (자율)

구조는 각자 고르고, 고른 구조와 이유를 `implementation_notes.md`에 쓴다. 코어타임에 설명할 수 있어야 한다.

| 구조 | 설명 | 장점 | 단점 |
|---|---|---|---|
| 단일 스레드 이벤트 루프 | `select`/`poll`/`epoll`로 요청을 한 줄로 세워 하나씩 처리 (실제 Redis 방식) | 잠금이 필요 없고 단순 | CPU 코어 하나만 씀, 한 요청이 오래 걸리면 모두 기다림 |
| 전체 잠금 | 스레드 여러 개 + `store` 전체에 `pthread_mutex` 하나 | 구현이 쉬움 | 요청이 몰리면 줄을 섬 |
| 칸별·구역별 잠금 | 칸 묶음마다 잠금 | 동시 처리량이 큼 | rehash와 함께 쓰기 어려움 |
| 읽기·쓰기 잠금 | `pthread_rwlock`. 읽기는 동시에, 쓰기는 혼자 | 읽기가 많은 캐시에 유리 | 지연 삭제와 통계 갱신 때문에 `get`도 쓰기가 될 수 있어 주의 |

- 여러 잠금을 쓰면 잠그는 순서를 문서에 고정한다. (교착 상태 방지)
- 잠금을 쥔 채로 네트워크 읽기·쓰기를 하지 않는다.
- 주기적 만료 정리와 영속성 기록도 같은 동시성 규칙 안에서 실행한다.
- rehash를 한 번에 하면 그 순간 O(n) 지연이 생긴다. 알려진 비용으로 적는다. (점진적 rehash는 차별화 후보)

## 13. 캐시 샘플 API (Phase 2)

원문 : "간단한 API 생성 후 API 응답 값을 미니 레디스에 저장하여 활용합니다."

### 13.1. 구성

- `slow_source` : 느린 원본(DB나 외부 API)을 흉내낸다. `get_product(id)`가 `SLOW_SOURCE_DELAY_MS`(기본 300)만큼 기다린 뒤 값을 돌려준다. 원본을 부른 횟수를 센다.
- `sample_api` : 포트 `3000`의 HTTP 서버. 미니 레디스에는 HTTP API로만 접근한다.

| 경로 | 설명 |
|---|---|
| `GET /products/{id}` | 캐시를 쓰는 조회 |
| `GET /products/{id}?cache=off` | 캐시를 쓰지 않는 조회 (성능 비교용) |
| `PUT /products/{id}` | 원본을 수정하고 `product:{id}` 캐시를 무효화 |
| `GET /demo/stats` | `{"originCallCount": n}` 원본 조회 횟수 (테스트·성능 비교용) |

### 13.2. 캐시 방식 : Cache-Aside

1. `product:{id}`를 미니 레디스에서 조회한다.
2. 있으면(적중) 그대로 응답한다.
3. 없으면(빗나감) 원본에서 가져와 `CACHE_TTL_MS`(기본 60000)와 함께 저장하고 응답한다.

- 응답에 `X-Cache: HIT` 또는 `X-Cache: MISS` 헤더를 붙인다.
- 원본이 실패하면 그 실패 응답을 캐시하지 않는다.
- 미니 레디스 서버가 꺼져 있거나 응답이 없으면 원본으로 바로 응답한다. 캐시 장애가 서비스 장애가 되지 않게 한다. (필수)

### 13.3. 갱신과 무효화

- 공통 검증 범위는 순차적인 갱신과 무효화다.
- `PUT /products/{id}`는 원본 갱신과 캐시 삭제를 모두 끝낸 뒤 성공을 돌려준다.
- 원본 갱신과 캐시 삭제 사이에는 유효한 기존 캐시 값이 반환될 수 있다.
- 원본 갱신과 조회가 겹칠 때의 캐시 일관성은 선택 기능이다. 지원한다면 "이전 값을 읽은 요청이 무효화 뒤에 그 값으로 캐시를 다시 채우는 상황"도 검증한다.
- 같은 빗나감 키로 요청이 몰릴 때 원본이 여러 번 불리는지는 확인만 하고, 막는 기능(stampede 방지)은 차별화 후보로 둔다.

## 14. 영속성 (Optional)

원문 : "Redis 서버가 다운되는 상황에서도 보관 중인 데이터를 최대한 안전하게 유지하려면 어떤 방식이 적합할지 검토합니다. (Optional)"

### 14.1. 방식 비교 (필수)

구현하지 않더라도 아래 방식을 비교해 `implementation_notes.md`에 "어떤 방식이 적합한지"를 적는다.

| 방식 | 설명 | 장점 | 단점 |
|---|---|---|---|
| 스냅샷 | 일정 주기로 전체 데이터를 파일로 저장 (실제 Redis RDB) | 파일이 작고 복구가 빠름 | 마지막 저장 이후 데이터는 잃음 |
| 명령 기록 | 쓰기 명령을 파일 끝에 계속 추가 (실제 Redis AOF) | 잃는 데이터가 적음 | 파일이 커지고 복구가 느림 |
| 둘 다 | 스냅샷 + 그 이후 명령 기록 | 둘의 장점 | 구현이 복잡 |

### 14.2. 구현한다면 : AOF 규칙

- 쓰기 연산(`set`, `delete`, `expire`, `delete_by_prefix`, 선택 함수의 `increase`·`flush`)이 성공했을 때만 파일에 JSON 한 줄씩 이어 적는다. 읽기는 기록하지 않는다.
- 기록 예 : `{"op":"set","key":"a","value":"1","expiresAtWallMs":1767000000000}`
- 만료 시각은 단조 시각이 아니라 실제 시각(밀리초)으로 적는다. 기록할 때 `실제 현재 시각 + (expires_at_ms - now_ms())`로 바꾸고, 복구할 때 반대로 바꾼다.
- 시작할 때 파일을 처음부터 읽어 `store` 공개 함수로 다시 적용한다. 복구 중에는 파일에 다시 기록하지 않는다.
- 복구 시 이미 만료된 항목은 적용하지 않는다.
- 마지막 줄이 잘려 있으면 읽을 수 있는 줄까지만 복구하고 경고를 남긴다.
- 기록 순서는 실행 순서와 같아야 한다. (12장 동기화 경계 안에서 기록)
- 파일 쓰기 시점(매번 즉시 `fsync` / 1초마다)은 안정성과 속도의 선택이므로 이유와 함께 적는다.
- 스냅샷이나 파일 재작성은 임시 파일에 쓴 뒤 `rename`으로 바꿔, 쓰는 도중 꺼져도 이전 파일이 깨지지 않게 한다.
- 경로는 상수 `AOF_FILE_PATH`에 두고, 실행 인자로 켜고 끌 수 있게 한다.
- 파일이 계속 커지는 문제(재작성, compaction)는 차별화 후보다.

## 15. 테스트 규칙

- 각자 자기가 작성한 코드의 테스트를 직접 만든다.
- 코어타임 병합 전에 자기 테스트뿐 아니라 다른 사람의 테스트도 서로의 구현에 돌려 모두 통과해야 한다. 통과하지 않는 곳이 규칙이 어긋난 곳이다.
- 테스트 도구는 지정하지 않는다. `make test` 한 줄로 단위 테스트가 실행되게 한다.
- TTL 단위 테스트는 실제로 기다리지 않고 `store_options_t.now_ms`에 가짜 시계를 끼워서 검증한다.

### 15.1. 필수 단위 테스트 (Phase 1, `store.h` 기준)

원문 : "데이터의 저장, 조회, 삭제 기능이 정상적으로 동작하는지 단위 테스트를 통해 검증합니다."

| 대상 | 주요 검증 내용 |
|---|---|
| 저장·조회 | 저장 후 조회, 덮어쓰기(`is_created` 참·거짓), 없는 키 조회, 빈 문자열 값 |
| 삭제 | 있는 키 삭제 후 조회 "없음", 없는 키 삭제는 거짓, 지운 키 다시 저장 |
| 충돌 | 같은 초기 칸에 들어가는 키 여러 개가 서로 독립적으로 저장·조회·삭제됨 (연결 앞·중간·끝) |
| rehash | 항목을 많이 넣어 칸이 늘어난 뒤에도 모든 값이 그대로 조회됨, `size`·`capacity` 변화 |
| TTL | 만료 직전 조회 성공, 정각·이후 "없음", `ttl_ms` 없이 덮어쓰면 만료 해제, TTL 교체, `store_expire`·`store_ttl` 값 |
| TTL 보존 | 잘못된 TTL로 다시 저장해 거부되면 기존 값과 만료 기한이 그대로임 |
| 지연 정리 | 만료 판정과 정리를 나눠 처리하는 구현은, 그 사이 같은 키를 다시 저장해도 새 값이 유지됨 |
| 무효화 | `store_delete_by_prefix`가 접두사가 같은 키만 지움, 지운 개수에 만료 키는 제외 |
| 만료 정리 | `store_remove_expired`가 읽히지 않은 만료 키를 정리, `max_count` 상한 |
| 개수·통계 | 저장·삭제·만료 후 `size`, `hit_count`·`miss_count`·`expired_count` |
| 메모리 | ASan 또는 Valgrind로 오류·누수 없음 (권장) |

### 15.3. 동시성 테스트

- TTL 없이 저장한 키 A를, TTL 없이 다른 키들을 동시에 저장하는 동안 반복 조회한다. A의 값이 계속 유지되고, 동시 저장이 끝난 뒤 성공한 저장을 모두 조회할 수 있어야 한다.
- 항목을 계속 넣어 rehash가 일어나는 동안 조회해도 값을 잃지 않는다.
- 같은 키를 동시에 삭제하면 `deleted: true`는 한 번만 나온다.
- 같은 키에 `PUT`과 `DELETE`를 섞어 보내도 서버가 죽지 않고 마지막 상태가 일관된다.
- (선택 `increase` 구현 시) 같은 키에 `increase`를 1000번 동시에 보내면 결과가 정확히 1000이다.
- 충돌·rehash 경로의 동시성은 구현별 테스트나 코드 리뷰에서 확인한다.

### 15.4. 캐시 예제와 성능 비교

캐시 예제 검증 :
- 첫 요청은 `MISS`이고 원본을 한 번 조회한다. 같은 요청을 다시 보내면 `HIT`이고 원본 조회 횟수가 그대로다.
- `PUT /products/{id}`가 끝난 뒤 다음 조회는 `MISS`이고, 원본을 한 번 더 조회하고, 새 값을 돌려준다.
- TTL이 지나면 다시 `MISS`다.
- 미니 레디스 서버를 끄고 호출해도 샘플 API가 응답한다.
- 캐시 ON의 조회·저장·무효화가 실제로 직접 구현한 해시 테이블까지 이어지는지 확인한다.

### 15.5. 엣지 케이스 체크리스트

키와 값 :
- 빈 키(에러), 256바이트 키(성공), 257바이트 키(에러)
- 한글·이모지·`/`·`?`·`%`·공백·콜론이 들어간 키 (URL 인코딩)
- `\u0000`이 들어간 키·값 (에러)
- 빈 문자열 값(저장 가능, "없음"과 구분), 1MiB 값(성공), 1MiB 초과 값(`413`)

해시 테이블 :
- 해시값이 같은 서로 다른 키
- 체이닝 중간 항목 삭제 / 개방 주소법이면 삭제 표시(tombstone) 뒤 항목 조회
- rehash 직전·직후(적재율 경계)의 저장·조회

TTL :
- `ttlMs`가 `0`, 음수, 소수, 문자열, `2147483648` (에러)
- 만료 시각 정각 조회 (만료)
- 만료된 키에 `expire`(거짓), 만료된 키에 `set`(새 항목)
- 만료가 있는 키를 `ttlMs` 없이 덮어쓰기 (만료 해제)
- 만료 정리가 도는 중에 같은 키를 읽고 쓰기

API와 서버 :
- 잘못된 JSON, 본문 없는 `PUT`, 최상위가 배열인 본문
- 없는 경로, 허용하지 않는 메서드
- 같은 `DELETE`를 두 번 호출
- 빈 문자열 접두사로 `POST /invalidate` (에러)
- 아무것도 없는 상태에서 조회·삭제·통계·접두사 삭제
- 요청 도중 클라이언트가 연결을 끊음 (서버가 죽지 않음)
- 서버 종료 중 요청이 들어옴

캐시 예제 :
- 원본이 실패하거나 느릴 때 (실패 응답은 캐시하지 않음)
- 같은 빗나감 키로 동시에 많은 요청이 몰릴 때
- 미니 레디스 서버가 꺼진 상태

영속성 (구현한 경우) :
- 파일이 없을 때 시작, 마지막 줄이 잘린 파일, 저장 도중 강제 종료, 재시작 후 만료 항목은 복구되지 않음

### 19.1. 용어 정리

- 해시 테이블 : 키를 해시 함수로 숫자로 바꿔, 그 숫자 자리의 칸에 값을 넣는 자료구조. 평균 O(1)로 찾는다
- 해시 함수 : 키를 정수로 바꾸는 함수
- 버킷(칸) : 해시 테이블에서 항목이 들어가는 자리 하나
- 충돌 : 서로 다른 키가 같은 칸 번호를 받는 일
- 체이닝 : 충돌한 항목들을 한 칸 안의 연결 리스트로 이어 두는 방식
- 개방 주소법 : 충돌하면 다른 빈칸을 찾아 넣는 방식
- 적재율 : 저장된 항목 수 ÷ 칸 개수. 높을수록 충돌이 잦다
- rehash : 칸 개수를 늘리고 모든 항목을 새 칸 번호로 다시 넣는 일
- TTL : Time To Live. 값을 보관하는 기간
- 단조 시계 : 시스템 시각을 바꿔도 거꾸로 가지 않는 시계
- 지연 삭제 : 만료된 항목을 누가 찾을 때 비로소 지우는 방식
- 주기적 정리 : 만료된 항목을 일정 주기로 찾아 지우는 방식
- 무효화 : 저장된 값을 더는 쓰지 않도록 지우거나 곧 사라지게 하는 일
- Cache-Aside : 먼저 캐시를 보고, 없으면 원본에서 가져와 캐시에 채우는 사용 방식
- 적중률 : 조회 중 캐시에 있었던(hit) 비율
- AOF : 쓰기 기록을 파일에 이어 적어 두었다가 재시작 때 다시 적용해 복구하는 방식 (Append Only File)
- 교착 상태 : 둘 이상의 작업이 서로의 잠금을 기다리며 영원히 멈춘 상태
- 시그니처 : 함수의 이름, 매개변수, 반환값 모양
- 코어타임 : 팀이 같이 모여 검토와 병합을 하는 시간
