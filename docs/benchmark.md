# 성능 비교 결과

> 협약 15.4 기준. 원본 결과와 스크립트는 `bench/`에 둔다.
> 실행 : 미니 레디스(`make run`)와 샘플 API(`make run-demo`)를 띄운 뒤 `python3 bench/run_bench.py 200 10`

## 측정 조건

| 항목 | 값 |
|---|---|
| 요청 수 | 시나리오·캐시 조합마다 200 |
| 동시 요청 수 | 10 |
| 키 종류 수 | 시나리오 2는 상품 100개, 시나리오 3은 요청마다 새 상품 |
| CACHE_TTL_MS | 60000 |
| SLOW_SOURCE_DELAY_MS | 300 |
| 연결 방식 (keep-alive 여부) | keep-alive 없음 (요청마다 연결을 닫음) |
| 측정 도구 | `bench/run_bench.py` (Python 3.10, 스레드 10개) |
| 컴퓨터 사양 | Intel Core Ultra 5 125H, Linux VM (CPU 2개, 메모리 3.8GiB), gcc 11.4 |

- 각 실행 전에 `POST /invalidate {"prefix": "product:"}`로 캐시를 비워 같은 초기 상태에서 시작한다.
- 시나리오 2는 난수 시드를 고정해 캐시 OFF·ON이 같은 요청 순서를 쓴다.

측정하지 않음 (권장 항목)

## 해석

- 시나리오 1 : 적중하면 원본(300ms)을 거치지 않아 평균 응답 시간이 약 17배 짧고 처리량이 약 16배 높다.
- 시나리오 1의 원본 조회가 1이 아니라 10인 이유 : 처음 동시에 들어온 10개 요청이 모두 빈 캐시를 보고 원본으로 갔다. 같은 빗나감 키로 요청이 몰리는 현상(stampede)이며, 막는 기능은 차별화 후보다. (협약 13.3)
- 시나리오 2 : 상품 100개 중 처음 보는 상품은 빗나가므로 적중률이 약 50%이고, p95는 원본 시간과 같다.
- 시나리오 3 : 적중이 없으면 캐시 조회·저장만큼 일이 늘지만, 원본 300ms에 비해 작아 OFF와 거의 같다 (캐시 오버헤드 약 1ms).
