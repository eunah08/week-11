# 성능 비교 결과

> 협약 15.4 기준. 원본 결과와 스크립트는 `bench/`에 둔다.
> 다시 재기 : `make bench` (캐시 ON/OFF), `make bench-store` (해시 테이블 100만 회)
> 원본 수치 : `bench/results/bench_result.json`

## 측정 조건

| 항목 | 값 |
|---|---|
| 요청 수 | 시나리오마다 200개 (첫 요청 1개는 혼자, 나머지 199개는 동시에) |
| 동시 요청 수 | 10 (변화 측정은 1, 10, 50) |
| 키 종류 수 | 시나리오 1 : 1개, 2 : 1~100 무작위(seed 42, 같은 순서), 3 : 200개 모두 다름 |
| CACHE_TTL_MS | 60000 |
| SLOW_SOURCE_DELAY_MS | 300 |
| 초기 상태 | 시나리오·캐시 설정마다 미니 레디스와 샘플 API를 새로 띄움 (빈 캐시, 원본 조회 0회) |
| 연결 방식 (keep-alive 여부) | keep-alive 없음. 요청마다 연결 (클라이언트 → 샘플 API, 샘플 API → 미니 레디스 모두) |
| 서버 스레드 | 미니 레디스 워커 8개, 샘플 API 워커 16개 |
| 측정 도구 | `bench/run_bench.py` (Python 3.14 표준 라이브러리, 스레드 풀) |
| 컴퓨터 사양 | Intel Core i5-8250U 1.60GHz (논리 코어 8), 메모리 16GB, Windows 11 + WSL2 Ubuntu |

## 해시 테이블 자체 성능 (저장·조회 100만 회)

`make bench-store` (`-O2`, 처음 칸 16개에서 시작, 네트워크 없음)

| 연산 | 횟수 | 전체 시간 | 1회 평균 | 초당 연산 |
|---|---|---|---|---|
| 저장 (새 키, rehash 포함) | 1,000,000 | 629.6 ms | 629.6 ns | 약 159만 |
| 저장 (덮어쓰기) | 1,000,000 | 252.4 ms | 252.4 ns | 약 396만 |
| 조회 (있는 키) | 1,000,000 | 245.6 ms | 245.6 ns | 약 407만 |
| 조회 (없는 키) | 1,000,000 | 243.5 ms | 243.5 ns | 약 411만 |

- 끝난 뒤 항목 100만 개, 칸 2,097,152개(적재율 약 0.48)였고, 있는 키는 100만 개 모두 적중했다.
- 시간에는 `snprintf`로 키를 만드는 시간과 값 복사(`malloc`)가 함께 들어 있다.
- 같은 코드로 앞서 잰 값은 저장(새 키) 932ns, 조회 373ns였다. WSL2에서는 실행마다 30% 안팎으로 흔들리므로 자릿수 정도로만 본다.
- 이 측정만 store를 직접 링크한다. 협약 6장("bench는 HTTP API로만")과 15.4("100만 회 측정")가 부딪혀서, 엔진만 재기 위한 예외로 두었다 (협약 수정 제안 대상).

## 해석

- **반복 조회(시나리오 1)** : 원본 조회가 200번에서 1번으로 줄었다. 평균 응답은 303.5ms에서 11.1ms로 약 27배 빨라졌고, 처리량은 약 26배 늘었다.
  - 적중 요청의 약 11ms는 "클라이언트 → 샘플 API → 미니 레디스" HTTP 연결 2번과 Python 클라이언트 비용이다.
  - 해시 테이블 조회 자체는 1µs 미만이다.
- **무작위 100개(시나리오 2)** : 처음 보는 상품은 MISS라서 적중률이 약 50%다. 평균은 대략 "적중 ≈ 10ms, 빗나감 ≈ 300ms"의 가중 평균으로 절반 수준이고, p95는 빗나감 요청이라 OFF와 같다.
  - 서로 다른 상품은 86개뿐인데 원본 조회가 100번인 이유가 있다. 아직 캐시에 없는 같은 상품을 동시에 요청하면 둘 다 MISS가 되어 원본이 여러 번 불린다(캐시 몰림, stampede). 막는 기능은 차별화 후보로 남겼다.
- **모두 새 상품(시나리오 3)** : 적중률이 0%라 캐시의 이득이 없다. 오버헤드(캐시 조회 + 저장, HTTP 왕복 2번)는 평균 약 1.5ms로, 원본 300ms에 비하면 작다.
- **동시 요청 수** : 동시 50에서는 샘플 API 워커(16개)보다 요청이 많다. 그래서 큐에서 기다리는 시간이 생기고 OFF 평균이 773ms까지 늘었다.
  - 캐시 ON은 적중 요청이 워커를 빨리 돌려줘서 같은 조건에서도 평균과 p95가 낮다.
  - 동시 수가 늘수록 적중률이 조금씩 떨어진다(39% → 27%). 같은 상품을 동시에 처음 요청하는 경우(stampede)가 늘기 때문이다.
- **첫 요청과 반복 요청** : 첫 요청은 ON/OFF 모두 약 302ms(원본 시간)로 같다. 캐시는 두 번째 요청부터 효과가 있다.
- **주의** : WSL2 안에서 클라이언트·샘플 API·미니 레디스를 한 컴퓨터에서 같이 돌렸다. 절대 수치보다 ON/OFF 비교에 의미가 있다.
